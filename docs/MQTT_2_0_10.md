# MQTT, Wetter und Sensoren in 2.0.10

Für Wemos / ESP8266 und klassischen ESP32. Die Uhr empfängt Daten von einem selbst konfigurierten MQTT-Broker. Home Assistant, ioBroker oder andere Publisher können dieselben Topics bedienen. MQTT bleibt ab Werk ausgeschaltet; es werden keine persönlichen Broker-Adressen oder Zugangsdaten in die BIN eingebaut.

## Verbindung und Anzeige

1. In der Weboberfläche als Admin anmelden. Bei noch nicht lesbarem Speicher den **Datenspeicher** unter **Eigene Animationen / Speicher** ausdrücklich einrichten. Vorhandene Dateien vorher sichern; kein automatisches Formatieren.
2. Unter **MQTT, Wetter und Sensoren** Broker-Hostname/IP, Port, gegebenenfalls Benutzer und Passwort eintragen. Der lokale MQTT-Zugang verwendet TCP ohne TLS; für das vertrauenswürdige LAN gedacht.
3. Wetter-Topic und gegebenenfalls separates Temperatur-Topic eintragen. Bis zu vier Sensorplätze haben jeweils Topic, Anzeigename und Einheit.
4. **MQTT speichern**. Ein leeres Passwortfeld behält das bisherige Passwort; die Lösch-Checkbox entfernt es ausdrücklich. Das gespeicherte Passwort wird nicht zurück an den Browser ausgegeben.
5. Im Modus **Automatik: gewählte Anzeigen** die gewünschten Kategorien ankreuzen: Uhrzeit, Animationen, Wetter, Sensorwerte. Danach **Einstellungen speichern**.

Für **nur Uhr und Wetter**: Uhrzeit/Wetter an, Animationen/Sensorwerte aus. Bei mehreren Sensoren wird je Runde ein weiterer aktueller Sensor angezeigt. Ohne aktuelle Daten wird die jeweilige Datenszene übersprungen; wenn keine gewählte Szene verfügbar ist, erscheint die Uhr. Verbindungsversuche erfolgen im Hintergrund mit Abstand; Animationen und Weboberfläche bleiben grundsätzlich bedienbar.

## Wetterdaten

Die folgenden Topic-Namen sind Beispiele und müssen zu deiner Installation passen; die Firmware schreibt keine fremden HA-/ioBroker-Konfigurationen um.

Wetter-Topic beispielsweise `haus/wetter`, als JSON:

```json
{"condition":"partlycloudy","temperature":17.2}
```

Temperaturen in **Grad Celsius** liefern. Ein zusätzlicher Temperatur-Topic ist bei diesem JSON nicht erforderlich. Alternativ auf dem Wetter-Topic nur den Zustand, etwa `sunny`, veröffentlichen und auf einem separaten Topic wie `haus/aussentemperatur` die Zahl `17.2` senden.

| Zustand | Darstellung |
| --- | --- |
| `sunny`, `sun`, `clear`, `sonne`, `sonnig` | Sonne |
| `cloudy`, `clouds`, `wolken`, `wolkig`, `bewoelkt` | Wolken |
| `partlycloudy`, `partly-cloudy` | Sonne und Wolken |
| `rainy`, `rain`, `pouring`, `regen` | Wolken und bewegte Regentropfen |
| `snowy`, `snow`, `snowy-rainy`, `schnee` | Schnee |
| `lightning`, `lightning-rainy`, `thunderstorm`, `gewitter` | Gewitter |
| `fog`, `nebel` | Nebel |
| `windy`, `windy-variant`, `wind` | Wind |
| `clear-night` | Mond |

Ohne Wetterzustand kann die Temperatur allein angezeigt werden. Die Temperatur liegt unter dem Symbol. Es gibt keinen direkten Wetteranbieter-Abruf auf der Uhr: HA/ioBroker beschaffen oder lesen die Daten und veröffentlichen sie per MQTT. Das hält Netzwerk-, Speicher- und HTTPS-Aufwand auf dem Wemos klein.

## Raumtemperaturen und andere Sensorwerte

Beispiel: Topic `haus/wohnzimmer/temperatur`, Anzeigename `Wohnzimmer`, Einheit `C`. Akzeptiert werden:

```text
21.4
```

oder beispielsweise

```json
{"value":21.4}
```

Auch `{"val":21.4}`, `{"state":21.4}`, kurze Textzustände und boolesche Zustände sind unterstützt. `true`/`false` innerhalb eines JSON-Wertfelds werden als `an`/`aus` dargestellt. Damit lassen sich etwa Temperatur, Luftfeuchtigkeit, CO2, Leistung oder ein Fensterzustand anzeigen. Numerische Werte erscheinen mit einer Nachkommastelle. Lange Beschriftungen/Werte laufen über die Matrix. Umlaute werden für die kleine Schrift vereinfacht, das Gradzeichen wird unterstützt.

`unknown`, `unavailable` und `null` sind keine gültigen Messwerte. Pro Nachricht werden höchstens **512 Bytes**, pro Topic höchstens **95 ASCII-Zeichen** verarbeitet. Keine Topic-Wildcards `+`/`#`; jeder der vier Sensorplätze erhält einen konkreten Topic. Bei JSON ist die Verschachtelung begrenzt.

## Home Assistant und ioBroker

**Home Assistant:** In einer Automation aktuelle Wetterzustände bzw. Sensorzustände mit der Aktion `mqtt.publish` auf die in der Uhr eingetragenen Topics senden. Die obigen JSON-/Zahlformate verwenden. Eine Entität in Home Assistant wird nicht automatisch durch ihren Namen zu einem MQTT-Topic; diese Zuordnung muss im Publisher erfolgen. Temperaturquellen gegebenenfalls vorher in Celsius umrechnen.

**ioBroker:** Die gewünschten Werte über den vorhandenen MQTT-Adapter oder ein eigenes Publish-Skript auf die konfigurierten Topics bringen. `val`-JSON wird neben einfachen Zahlen unterstützt. Broker-/Adapterinstanz und Datenpunkte hängen von der eigenen Installation ab.

Optional veröffentlicht die Uhr per Home-Assistant-Discovery zwei Diagnose-Entitäten: **Firmware** und **WLAN-Signal**. Standardpräfix `homeassistant`, konfigurierbar. Standardmäßig entsteht eine individuelle Topic-Basis `chaosuhr/<geraetekennung>`; eine eigene Basis ist möglich. Darunter liegen `/state` für Diagnose-JSON und `/availability` mit `online`/`offline` einschließlich Last Will. Discovery-Daten werden retained veröffentlicht. Die MQTT-Anbindung dieser Fassung dient Datenempfang und Diagnose, nicht der Fernsteuerung von Einstellungen.

Offizielle Grundlagen: [Home Assistant MQTT und Discovery](https://www.home-assistant.io/integrations/mqtt/), [MQTT Sensor](https://www.home-assistant.io/integrations/sensor.mqtt/), [ioBroker MQTT-Adapter](https://github.com/ioBroker/ioBroker.mqtt).

## Alter der Daten und Speicherung

Die Zeitgrenze gilt **ab Empfang auf der Uhr**, standardmäßig 1800 Sekunden. Danach wird eine Datenszene übersprungen. Die Quelle sollte regelmäßig aktualisieren, beispielsweise alle fünf Minuten. Retained-Nachrichten liefern nach Wiederverbindung sofort einen Wert; ohne Quellzeitstempel lässt sich dessen ursprüngliches Alter aus dem Empfang allein nicht erkennen.

MQTT-Konfiguration wird erst nach Prüfung atomar im vorhandenen LittleFS gespeichert. Für Einstellungen und Zugangsjournal bleiben bei Animations-Uploads 12 KiB Reserve. Auf dem ESP32 ist der Dateisystembereich kleiner als auf dem Wemos; acht Plätze bedeuten nicht, dass acht maximal große Dateien gleichzeitig passen.

MQTT-Passwörter müssen für Wiederverbindungen auf dem Gerät gespeichert werden und sind deshalb weiterhin in einem vollständigen Flash-Dump enthalten. Sie erscheinen nicht in Status-API oder Einstellungssicherung. JSON-Einstellungssicherung enthält Anzeigeoptionen, aber weder MQTT-Verbindungsdaten noch den physischen LED-Datenpin; diese werden am Zielgerät separat eingerichtet.
